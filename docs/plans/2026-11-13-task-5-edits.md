## Steps

### Step 1 (5.1): Route paths to sessions

| File | What it does |
| --- | --- |
| `src/recorder/session/assignment-relative-path.ts` | A server path relative to an assignment root, or `null` outside it |
| `src/recorder/session/session-router.ts` | The innermost root owns a path, as in VS Code; returns the session and the assignment-relative path |
| `src/recorder/wiring/recordability-filter.ts` | Never records the recorder's own files: anything in `.provenance/`, and the manifest |

Ported from VS Code's `session/session-router.ts` and `session/assignment-relative-path.ts`.
JupyterLab paths are already server-relative with forward slashes, so there is no OS path
handling. A look-alike prefix such as `hw10` is not treated as inside `hw1`.

### Step 2 (5.3): Plain text files, and a safety net for both kinds of document

| File | What it does |
| --- | --- |
| `src/recorder/events/doc-events.ts` | Ported from VS Code: `doc.open` (inline up to 64 KB), `doc.save`, and edits as line/character ranges, bottom to top. Also reads JupyterLab's Quill-style deltas |
| `src/recorder/wiring/file-editor-wiring.ts` | `FileWiring`, the text-file counterpart of `NotebookWiring` |
| `src/recorder/wiring/notebook-wiring.ts` | Now shares `doc.open` with text files, and has the safety net below |

**The safety net.** Each change handler is also given the document's current text from
JupyterLab. If that text already matches what was recorded, the change was already absorbed,
for example when cells merge and the list change arrives first, so it is skipped. If applying
the change would not produce that text, one corrective edit replaces that cell or file instead.
The recorded text therefore stays exact even if signals arrive in an unexpected order.

### Step 3 (5.2): Connect JupyterLab

| File | What it does |
| --- | --- |
| `src/recorder/wiring/jupyter-documents.ts` | Follows `INotebookTracker` and `IEditorTracker`. Waits for each document to load, then records cell edits, cell list changes, saves and closes |
| `src/recorder/session/recording-session.ts` | Each session now has its own notebook and file wiring, and drops document events that arrive after it ends |
| `src/index.ts` | Requires the notebook and editor trackers, and reads saved files back through JupyterLab's contents API |
| `tests/support/fake-jupyter.ts` | Fake signals, shared models, contexts, widgets and trackers for tests |

Behaviors, each tested:

- Nothing is recorded before a document has loaded, or for paths outside every assignment folder.
- A document open in several views is recorded once, and closed when its last view closes.
- A rename closes the old path and opens the new one.
- Notebooks opened in the text editor are left to the notebook tracker.
- Documents already open when recording starts are picked up.
- `doc.save` hashes the file read back from disk, as the plan requires, not the in-memory model.
- Disposing stops every listener.

The adapter is typed against small interfaces that JupyterLab's real objects satisfy. Two
JupyterLab types are looser than the runtime objects: the editor's shared model is declared as
a generic document, so its source and change event are checked at runtime.

## Verification

**Automated:** 114 TypeScript tests (74 to-do stubs) and 32 Python tests pass; typecheck, ESLint,
Prettier, ruff and strict mypy are clean.

**Real JupyterLab 4.5.0.** Headless Chrome was driven through the Chrome DevTools Protocol, with
Node's built-in WebSocket and no new dependency. Real key input was typed into the first cell of
a notebook, including an emoji, and into a `.py` file, and each was saved with Ctrl+S. The logs
were then checked with log-core:

| Check | Result |
| --- | --- |
| Logs parse and the chain validates | Yes, for both sessions |
| One `doc.change` per typed character | Yes: 26 for the notebook, 14 for the `.py` file |
| Replaying the notebook's events reproduces the view of the `.ipynb` on disk | Exactly, emoji included |
| Replaying the `.py` file's events reproduces the file on disk | Exactly |
| `doc.save` hashes match the saved files | Yes |

This confirms the assumption flagged in the team tasks: JupyterLab's shared-cell changes are
Yjs-style deltas with UTF-16 offsets, as `sourceChanged` expects.

The test root key was used for that build only and restored at once. The committed source and
the final build contain the real dev root key, both checked.

## Known gaps

- **Reloads from disk are recorded as typing.** When JupyterLab reloads a file changed on disk,
  the reload arrives as ordinary shared-model changes and is recorded as `doc.change`, not
  `fs.external_change`. Task 6.4 fixes this.
- **`source` is always `'typed'`.** Paste detection is Task 6.3.
- **Real-time collaboration** would record other users' edits as this student's. Decision 6 is
  still open; the plan recommends requiring it off for v1.
- **Not verified on JupyterLab 4.4.5** (Data 101 and 102). Task 9.2.
- **The browser driver** could not move the cursor with Ctrl+End or insert a newline with Enter,
  so the typing landed at the start of the cell. This is a limit of the test driver, not the
  recorder: the replayed log still matched the saved files exactly.
