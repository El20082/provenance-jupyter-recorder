# Initial Build Plan (Plan 0 of the provjup series)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Take `provjup` from a skeleton of stubs to a JupyterLab recorder whose sealed bundle passes the real Provenance analyzer. **Current target: Data 100, Data 101 and Data 102, with Data 100 first.** This plan orders the work, names what blocks it, and defines each step's gate. Each step in `docs/design.md` §9 then gets its own detailed plan in this folder (`docs/plans/README.md`).

**Architecture:** The TypeScript frontend (`src/`) does all recording and format work by importing `log-core` through `src/core/`. The Python server extension (`provjup/`) only moves bytes, because a browser cannot write files, watch a disk or read the installed extension tree. Notebooks are recorded as the `ipynb-source-v1` text view, with no new event types (README, "Notebook text view").

**Tech Stack:** TypeScript, JupyterLab 4 plugin APIs, CodeMirror, Vitest, ESLint, Prettier, Python 3.11+, Jupyter Server, hatchling, ruff, mypy, pytest. Runtime dependencies still need approval (Task 3).

**Main reference:** The VS Code recorder, `packages/recorder` in the monorepo. See "Reference Map".

## Global Constraints

- **Student workflow (decided).** Students install the extension in JupyterLab and create the zip with Otter at the end of their session. There is no Prepare Submission Bundle command, even though VS Code has one. The only other action is enrolling once, which contributor tracking requires and which never blocks recording.
- **Master secret (decided).** At rest it never leaves the student's home directory: a `0600` file in a `0700` folder under the Jupyter data directory. This replaces key-management §4.4's "never leaves the machine" for `provjup`. It never enters a workspace, `.provenance/`, a log, a bundle or browser storage.
- **Format contract (CLAUDE.md).** `log-core` owns the format. Never re-implement it here, and never edit a vector. Format changes land in the monorepo first, with explicit approval.
- **`provjup/` never builds or interprets log entries.** The one exception is `extension_hash`.
- **Every log entry goes through `session-host.ts`.** Events are append-only.
- **Maximum granularity (decided).** The recorder exists to recreate how a student worked, letter by letter. Prefer the finest capture available, and never accept avoidable delay or merged events to simplify the design.
- **Keystroke path p99 under 1 ms.** No signing or canonicalizing on it.
- **Recording scope.** Only a verified assignment root, and only cell sources: no outputs, execution counts or kernel activity. Decision 1 reopens this for Task 10; until it is approved, the rule stands.
- **Privacy.** The frontend talks only to its own Jupyter server. The master secret never enters a workspace, `.provenance/`, a log or a bundle. Honeypot answers never reach the recorder, the manifest or the bundle.
- **Identity failure never blocks recording.**
- **Every listener, timer and watcher has a dispose path.**
- **Ship order.** The analyzer's check 8 change deploys before any Jupyter recorder ships, or old analyzers report false "edited outside the recording" mismatches.

## Meeting Questions

Answers to the open questions in the meeting notes, for discussion at the next meeting. These are recommendations, not decisions. They conflict with the README and `docs/design.md`, which say "no new event types" and exclude execution; those stay as they are until the meeting decides.

### What new log types do we need?

**Recommendation: one new event, `cell.execute`, in the existing `.slog`. No separate per-cell JSON file.**

- **Why not a per-cell JSON file.** A file holding each block's current state is rewritten in place, so it breaks the append-only, hash-chained rule. It also duplicates what events already give: the analyzer can compute run counts and each cell's latest state from the event stream.
- **Why not reuse `terminal.command`.** Its payload (`terminal_id`, `command`, `exit_code`) would fit without a format change, but `no_intermediate_errors` reads those events as shell commands. Mixing cell runs in would change that flag's meaning.
- **Proposed payload (names are a draft):** `path`, `cell_id`, `source_sha256`, `started_t`, `ended_t`, `success`, `error_name` and `output`.
- **Outputs: digest only for v1.** Store `sha256`, byte size and MIME types, plus capped error text. Full outputs can include large images, data and personal information, and they say little about how the code was written. If staff need more text, reuse the recorder's existing inline cap.
- **Compatibility.** `ndjson.ts` does not reject unknown `kind` values, and reconstruction skips kinds it does not use, so older analyzers should load these bundles. Task 10 confirms this with a test.
- **Signals available.** `NotebookActions` provides `executionScheduled`, `executed` (with `success` and `error`), `selectionExecuted` and `outputCleared`. None carries timing, so stamp both ends with the recorder's injected clock. Runs are infrequent, so this stays off the keystroke path.

### How do we show this in the analyzer?

**Recommendation: keep replay as it is, and render the text view as cells (monorepo item 6).** Split the replayed text on the `# %% [type] id=` separators, then show `cell.execute` as markers in the replay lanes, timeline and event sidebar. Show a cell's run count and output digest in a side panel. Do not try to re-render real outputs.

### Is reconstructing the notebook at each instant too slow?

**Probably not, because the analyzer does not rebuild a notebook.** It replays one text file, the view, through machinery that already exists:

- `reconstruct-file.ts` stores content by line, so a single-line edit costs about one line, not the whole file.
- `engine-core.ts` caches replay state every `CHECKPOINT_EVERY` events, so a seek starts from the nearest checkpoint, not from zero.
- Full reconstructions are memoized per `EventIndex`.

This is unmeasured for notebooks. Moving or deleting a cell is a multi-line edit, which takes the slower path. Task 10 measures it on a real course notebook before anyone adds an optimization.

### How should we log? Are Jupyter's own logs usable?

**Recommendation: use JupyterLab signals as the source, and treat Jupyter's own logs as untrusted hints at most.** None of them has a hash chain.

| Source | What it holds | Verdict |
| --- | --- | --- |
| Jupyter Server events (`contents_service`) | `action`, `path`, `source_path`; no content | Not evidence. `POST api/events` lets a client emit events. Our server watcher already covers this. |
| Cell `execution` metadata (`recordTiming`) | Timing inside the `.ipynb` | Off by default, and students can edit the file. Do not rely on it. |
| `.ipynb_checkpoints` | A saved copy of the notebook | A recovery copy, not a history. |
| `.OTTER_LOG` | Pickled check, export and auth events | Student-writable, with no edit data. Never unpickle it in the analyzer: a crafted pickle can run code. |

**Git diffs: no as the main log.** They capture state only at commits, so they lose typing, pastes and timing, and `.ipynb` diffs carry output and metadata noise. Keep `git.event` as a supporting signal.

**Security matches the other recorders:** tampering is detected, not prevented (recorder PRD NG1). A student can disable an extension on a machine they control, so on a hub staff install and lock it.

## Otter Findings

`docs/otter_for_provenance.md` targets a simpler recorder than this one. Checked against the `otter-grader` 7.0.0 source in the sibling checkout:

- **Keep `.provenance/`.** The guide's visible-folder rule comes from Jupyter's Contents API rejecting hidden paths. `provjup` writes through its own server extension, so it does not apply.
- **`.provenance/` can still reach the zip.** Otter globs `f"{file}/**/*.*"`. A local test of that pattern with `.provenance` picked up `session-a.slog`, `session-a.slog.meta`, `manifest.json` and `manifest.sig`, because the literal dot in the prefix matches. Only this glob was tested, not a full export. Otter Assign's `files` copies directories with `copytree`, so a dot-folder should work; that comes from reading the source, not a run.
- **The rolling seal fits this path.** Nobody runs a seal command inside `grader.export`, the same problem the rolling seal solved for git submissions. The zip would carry `manifest-<session>.json` and `.sig`.
- **The folder must exist at export.** A missing folder raises `FileNotFoundError`, so assignments need a placeholder or students without the extension cannot submit. Placeholder needs an extension and no leading dot.
- **Do not adopt the guide's sketch.** Its `.jsonl` chunks have no hash chain, and it records cell source on every run outside the signed log. Task 10 covers the same signals inside the chain, if approved.
- **No ingest adapter is needed for Gradescope.** `provgate` forwards the bulk export to `ingest:gradescope`, whose `discoverRepoScopes` strips the `.provenance/` prefix and drops stray files. The golden bundle rebuilt in Otter's layout, with `.OTTER_LOG`, `__zip_filename__`, a PDF and a placeholder added, loaded and passed the required checks through that code. It ran the scope and loader functions directly, not the deployed server.
- **The raw zip only works through that path.** Passed straight to `loadBundle`, as the analyzer's `/local` route would, it fails with `missing_manifest`.
- **A student with only the placeholder is skipped as `no_seal`,** but stays on the roster. Their Gradescope submission is unaffected.

### Otter integration issues

Most of `docs/otter_for_provenance.md`'s storage and grading advice does not apply here. Its export mechanism does. These issues remain, most serious first:

1. **Export-time seals are provisional.** `final: true` is written only at `dispose()`, and a student exports with the notebook still open. Check 8 then treats the notebook's hash as non-binding, and entries after the last checkpoint look like honest growth (`rolling-manifest.ts`, "the append hole"). **Accepted:** students run no seal step, so Otter submissions are weaker evidence than a classic sealed bundle. Tell staff this in the deployment guide.
2. **An atomic write can crash the export.** Otter globs the folder, then calls `zf.write` on each path. A `.tmp` file listed by the glob and renamed before its write raises `FileNotFoundError`, which stops the student submitting. Rolling seals rewrite on saves and checkpoints, so students can hit this. Fix in `provjup/fs/atomic_write.py`: stage temp files outside `.provenance/` on the same filesystem.
3. **The newest work can miss the zip.** Otter reads disk, and the roll on save waits behind a 1 s debounce. A student who saves and immediately runs export can ship a seal older than the notebook. On `executionScheduled`, flush the log and roll the seal; this narrows the gap but cannot close it, because the kernel does not wait for the browser.
4. **An unsaved notebook exports stale.** Otter's docstring says `force_save` works only in classic Notebook. **Decided:** the recorder saves a dirty notebook on every cell run, then flushes the log and rolls the seal. It does not save on the writer's own flush timer, which fires every second and would rewrite the notebook and queue a workspace-walking seal roll almost continuously. The save still races the kernel, so Task 7 tests it against the export cell.
5. **The recorder must sit beside the notebook.** `.provenance` resolves against the kernel's working directory, so a manifest in a parent folder or a `%cd` raises `FileNotFoundError`. Put `.provenance-manifest` in the notebook's folder.
6. **`files: - .provenance` can leak staff logs.** Otter Assign copies the whole master folder to every student. Stage it with only the placeholder, and add a check before distribution.
7. **Assignments need two more entries.** `.provenance-manifest` must also be listed under `files`, or recording never activates.
8. **Check 8 depends on monorepo items 3 and 4.** Students submit the `.ipynb` with outputs, so it must be compared by view hash, and the rolling manifest must list the notebook.


### Enrollment and secret storage

Contributor tracking is required, so enrollment stays. Manifests keep the default `policy.enrollment.required: true`, and `provjup` ports the identity path. Only sessions with a verified `student_ref` can attribute a finding to a person.

**Enrollment needs one student action.** `POST /identity/credential` requires the student's own Google sign-in and refuses API tokens and admin view-as, on purpose. A staff script or hub service cannot do it for them. One credential serves every course, so this happens once per home directory.

**The flow matches VS Code (decided).** The nudge offers Enroll, Show My Key and Later. The student runs **Show My Enrollment Key**, signs in at `/enroll`, pastes the key, and pastes the returned token into **Import Enrollment Token**. The extension makes no network call, as in recorder PRD NG2. Installation instructions follow the monorepo's `docs/student-guide.md` wherever JupyterLab allows.

- **DataHub login cannot replace this for v1.** DataHub signs students in through Canvas, while Provenance keys identity on the Google `sub`. Reusing the hub login would need a new trusted route on the Provenance server, a matching hub service from the DataHub team, and a way to stop one student splitting into two `student_ref`s across editors. Decided: keep Google sign-in.
- **Timing matters.** A session records its identity at `session.start`, which is signed and cannot be added later. Work before enrollment stays unattributed, so show the notice at first activation. Recording still starts immediately.
- **Secret location.** Use `~/.local/share/jupyter/provjup/identity.json`, resolved through Jupyter's data directory, with the credential beside it. `provnvim`'s store is the precedent.
- **Keep it out of submissions.** Refuse to activate if an assignment root contains the identity file, for example a manifest placed in the home directory itself. Otter only zips `.provenance`, so the normal export cannot include it.
- **The browser must see the secret briefly.** All signing runs in the frontend, so the secret reaches browser memory through `provjup`'s authenticated route to derive the student key. It is never persisted there. This is why the rule says "at rest".
- **Weaker than an OS vault.** Anything running as the student can read the file, including kernel code from a notebook, and so can anyone with admin access to home directories. A leaked secret can sign as that student. Accepted for hub use; state it in the staff guide.
- **Unchanged cryptography.** Key derivation stays as pinned in `student-keys.json`, so this is not a format change. A second hub or a lost file means enrolling again, and the same Google account returns the same `student_ref`.
- **Back up and restore are not needed.** Re-enrolling covers a lost secret, so those commands are not ported.

### Hub and heartbeat issues

- **Students probably cannot keep an install on DataHub.** Its FAQ says user-installed packages last only as long as the server. Staff should get `provjup` into the course's hub image, which also means no install step for students. Confirm the process with DataHub support, along with whether `~/.local/share/jupyter` survives between servers; if it does not, the identity file needs another home-directory path.
- **DataHub shuts servers down.** The public `hub/values.yaml` (staging branch; a course hub may override it) sets a server's maximum age to 8 hours regardless of activity, and shuts down a server after 30 minutes without activity. The recorder must survive both, which Task 7's recovery tests cover.
- **Every heartbeat must be logged (decided).** Emit `session.heartbeat` every 30 s through `session-host.ts`, as VS Code does. Browsers throttle timers in hidden tabs, and VS Code's logic reads a gap of twice the interval as a suspend, so a plain port would drop heartbeats and log false `session.resumed` events. Drive the timer from a Web Worker, and test hidden tabs in real browsers.
- **A heartbeat cannot exist while the page is closed.** Closed tabs, sleeping laptops and culled servers stay real gaps. The next session records them.
- **Heartbeat traffic may keep hub servers alive.** Regular API calls could count as activity toward the 30-minute shutdown, so an abandoned tab could hold a DataHub server open for up to 8 hours. Test this, and mark the log routes as not tracking activity if so.

**Do not use from that guide:** the Contents API writer, `.jsonl` chunks, the `provenance/` folder name, the placeholder at that path, or the `ProvenanceReport` plugin. `provgate` already moves submissions into Provenance, so nothing has to run during grading.

**Still unverified:** a real Gradescope upload keeping `.provenance/`. The monorepo's `select-entries.ts` lists that nested layout as observed, but only a real submission confirms it for a notebook assignment. Upload size limits are also unchecked.

## Gaps Found While Planning

- **No `extension_hash` vectors exist.** CLAUDE.md and `docs/design.md` say conformance vectors gate it, but `tools/export-conformance-vectors.ts` exports none.
- **The three implementations sort differently.** VS Code and `update-hashes` use `localeCompare`, `provjet` uses ordinal comparison, and `provnvim` uses byte order. These can disagree on the same tree, for example on mixed-case paths, so the Python version needs one defined order.
- **`session.start.vscode` is superseded.** `session.start` 2.0 carries `host`, so this recorder should not copy the siblings' `vscode` workaround.
