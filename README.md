# provenance-jupyter-recorder

A JupyterLab extension that records a tamper-evident Provenance log (`.slog`) while a
student works on a notebook assignment. It is the fourth Provenance recorder, after
VS Code (in the `provenance` monorepo), JetBrains (`provenance-jetbrains-recorder`)
and Neovim (`provenance-neovim-recorder`).

Its bundles are designed to be format-compatible with the other recorders, so the same
analyzer, validation checks and heuristics can read them.

> **Status: skeleton only. Nothing is implemented and the project does not build yet.**
> Each source and test file is a stub describing its job. `package.json` and `pyproject.toml`
> declare no dependencies, and `log-core` is not wired in. See
> [Open decisions](#open-decisions).

---

## What it does

- Activates only inside a folder containing a signed `.provenance-manifest`
  (or `provenance-manifest`) whose signatures trace back to the embedded root key.
  Anywhere else it does nothing.
- Records editing activity in notebooks (`.ipynb`) and ordinary text files opened
  in JupyterLab: opens, edits, saves, pastes, focus, external changes on disk,
  terminal commands, heartbeats.
- Chains every event with SHA-256 and signs checkpoints and the final bundle with
  a per-session ed25519 key. This is the same format as the VS Code recorder, from
  the same `log-core` code.
- **Provenance: Prepare Submission Bundle** seals a `.zip` for upload.

### What it does not record

- **Cell outputs, execution counts, kernel activity, notebook metadata.** Only cell
  *sources* are recorded (see [Notebook text view](#notebook-text-view-ipynb-source-v1)).
- Anything outside an activated assignment folder.
- Anything over the network. The frontend talks only to its own Jupyter server
  (recorder PRD NG2).
- Notebooks opened in VS Code, Colab, or classic Notebook 6 (out of scope for v1).

## How it works

```
 ┌──────────────── browser (JupyterLab frontend, TypeScript) ────────────────┐
 │  notebook/editor signals ─► text-view projection ─► SessionHost.emit()     │
 │  (cell edits, paste,          (ipynb-source-v1)       │  log-core:         │
 │   focus, save, terminal)                              │  chainEntry, sign, │
 │                                                       ▼  checkpoints       │
 │                                             append-only line buffer        │
 └───────────────────────────────────────────────┬────────────────────────────┘
                                                 │ REST (same-origin)
 ┌───────────────── Jupyter server extension (Python) ────────────────────────┐
 │  append lines to .provenance/session-<uuid>.slog (atomic, ordered)          │
 │  watch tracked files on disk ─► raw bytes back to frontend                  │
 │  compute extension_hash over the installed labextension tree                │
 │  write sealed bundle zip                                                    │
 └─────────────────────────────────────────────────────────────────────────────┘
```

**Rule: all format logic lives in the TypeScript frontend, via `log-core`.**
Chaining, canonicalization, signing, the text-view projection and the payload
builders all run there. The Python side only moves bytes. It never builds,
hashes or interprets log entries.

The one exception is `extension_hash`, which needs the installed file tree a
browser can't read. Its Python implementation is held to the monorepo's
conformance vectors.

first; this repo then picks it up.

## Notebook text view (`ipynb-source-v1`)

A notebook isn't recorded as its JSON file. It is recorded as a deterministic plain-text
**view** of its cell sources, and every `doc.*` event for an `.ipynb` path refers to
that view.

**Draft definition.** It must be pinned in `log-core` with test vectors before use.

```
view(nb) = concat over cells, in notebook order, of:
             "# %% [" + cell_type + "] id=" + cell_id + "\n"
             + source
             + "\n"
```

- `cell_type` ∈ `code | markdown | raw`; `cell_id` is the nbformat ≥ 4.5 cell `id`.
- `source` is the cell source as a single string (nbformat's line array joined).
- A notebook with zero cells has the empty string as its view.
- Outputs, `execution_count`, cell and notebook metadata, and attachments are **excluded**.

Unresolved edge cases: notebooks older than format 4.5 (no cell ids), markdown lines
that begin with `# %%`, and `\r\n` inside cell sources.

Example:

```text
# %% [code] id=a1b2c3
import numpy as np
x = np.arange(10)
# %% [markdown] id=d4e5f6
## Question 2
```

### Mapping onto existing events

| Notebook activity | Event | Notes |
|---|---|---|
| Notebook opened | `doc.open` | `content` = view, `sha256` = sha256(view), **`view: "ipynb-source-v1"`** |
| Typing in a cell | `doc.change` | The cell's offset-based source delta is translated to a line/char `Range` in the view |
| Paste into a cell | `doc.change` + `paste` | Classified by the shared three-signal logic |
| Add, delete or move cell | `doc.change` | Shown as text insert/delete of the cell block; `internal-move` already covers moves |
| Change cell type | `doc.change` | Rewrites the separator line |
| Save | `doc.save` | `sha256` = sha256(view of the saved notebook), computed from the saved file |
| File changed on disk | `fs.external_change` | Server reports the raw bytes; frontend computes the view and compares it with the expected content |
| Output-only change on disk | *nothing* | The view didn't change |

There are **no new event types.** Ordinary text files (`.py`, `.csv`, …) opened in
JupyterLab's text editor are recorded exactly as VS Code records them.

### Derived flags (analyzer only, not logged events)

Flags are computed by the analyzer from recorded events. The recorder doesn't emit
them, and they add nothing to the `.slog`.

| Flag | Fires when | Input | Honeypot data lives |
|---|---|---|---|
| `honeypot_similarity` **(proposed)** | A cell's text, at any recorded point or at submission, matches or closely resembles a staff-defined honeypot answer | Cell text rebuilt from `doc.open`, `doc.change`, `paste` and `fs.external_change` | Staff-side analyzer or server config, per assignment. **Never in the manifest, the recorder or the bundle.** |

Evidence shown for each hit:

- honeypot id, cell id and match score
- when the text first appeared
- how it arrived: typed, pasted, or external change
- whether it was still present at submission

A hit is a prompt for human review, not proof of misconduct. It must not produce a
finding on its own.

## On-disk layout (identical to the other recorders)

```
<assignment-root>/
├── .provenance-manifest            # signed by course staff; activates recording
├── hw1.ipynb
└── .provenance/
    ├── session-<uuid>.slog         # ndjson, hash-chained, append-only
    ├── session-<uuid>.slog.meta    # encrypted session private key, checkpoints
    ├── manifest-<session>.json     # rolling seal (git-submitted assignments)
    ├── manifest.json               # written at seal time (signed BundleManifest)
    └── manifest.sig
```

Sealed bundle: `<assignment_id>-bundle-<timestamp>.zip`, containing `.provenance/` plus
the in-scope submission files at their assignment-relative paths.

## Security model

Same as the other recorders (monorepo `docs/key-management.md`):

| Key | Here |
|---|---|
| Root public key | Embedded in the frontend bundle at build time |
| Session keypair | Generated in the browser per session; private key kept in memory, persisted only encrypted (manifest-derived key) in `.slog.meta` |
| Student master secret | **Open decision.** No OS keychain inside a JupyterHub container. |
| `extension_hash` | Computed server-side over the installed labextension tree; staff add it to the analyzer allowlist |

Not tamper-proof (recorder PRD §6): casual and moderate tampering is detected, and a
full forgery costs more than doing the assignment. On a hub, the plugin should be
installed in the image by staff and locked with `jupyter labextension lock`.

## Required monorepo changes

These land in `ProvenanceTools/provenance` first. None have been made. All format
items need explicit approval.

1. `log-core`: `HostInfo.editor` gains `'jupyterlab'`. *(approved)*
2. `log-core`: optional `view` field on `DocOpenPayload`; `ipynb-source-v1` projection
   function plus test vectors.
3. `log-core`: signed bundle manifest gains the view sha256 per `.ipynb`.
4. `analysis-core`: check 8 compares view hashes for `view`-tagged paths.
   **Deploy before any Jupyter recorder ships**, or old analyzers will report false
   "edited outside the recording" mismatches.
5. `analysis-core`: treat `nbgitpuller` updates like git for external-change explanations.
6. `analyzer`: render replayed `ipynb-source-v1` text as cells (UI only).
7. `/architecture`: ecosystem and roadmap diagrams, plus node details.
8. `known-good-extension-hashes.json`: add each release's hash.
9. `analysis-core`: add the `honeypot_similarity` heuristic and register it in
   `known-flag-ids.ts`. Add a tuning-UI entry, heuristic docs and an `/architecture`
   update. No format change is needed.
10. `analyzer` or `server`: add staff-only storage and editing for each assignment's
    honeypot answers.

## Open decisions

1. **Outputs and execution:** confirm they stay out of scope (current design assumes yes).
2. **Deployment target:** remote JupyterHub (Berkeley DataHub) vs local Jupyter.
3. **Student secret storage:** the `provnvim` precedent is a `0600` file outside every
   workspace, and the VS Code and `provjet` precedent is an OS vault. On a hub, a file
   sits on university storage, which conflicts with key-management §4.4 "never leaves
   the student's machine".
4. **Submission path:** a separate bundle upload, or included in Otter's
   `grader.export` zip (needs an ingest adapter).
5. **VS Code notebooks:** whether to fix the monorepo recorder's notebook gap using
   the same text view.
6. **Real-time collaboration:** filter edits from other users, or require it disabled.
7. **Shared helpers:** copy the VS Code pure modules, or upstream them into a package.
8. **`log-core` delivery:** submodule (proposed) vs npm publish.
9. **Honeypot matching:**
   - What counts as "similar": exact, whitespace-normalized, or fuzzy token match,
     and at what threshold?
   - What is a honeypot here: a planted wrong answer, a fake source or a trap
     instruction?
   - Does comparing student text fit recorder PRD NG5 and the rule against analyzing
     student code?
